# OmniNull audit, 2026-11-06

Read-only audit of the repo at `1.8.109` plus the in-flight agy/Google maker change (not reviewed for correctness), the live hub on CT 150, and the Aico integration. No code was changed.

## Verdict

The detection core is sound. Its classing (page, record or digest, in `detector/class.go`), its tuning held as live data and its floor drill are the right ideas. The problem is the weight around that core. It is about 13K lines of detection inside about 85K lines of hub Go, 24K of console, 31K of agent C and 8K of Rust screen-sharing. On top of that sit a release and trust layer built for an enterprise product with many operators: a separate response-authority service, routine signing keys, a forced-command install key, canaries, owner-approval plumbing that has since been removed, and 17 Nightshift routes of which 2 are still called.

Results over 30 days:
- **Real threats caught: none.** No resolution in the hub's history (5,796 findings since 2026-09-14) is a true positive.
- **Pages under today's tuning: 5**, all false. One came from the hub's own tests. One was a perl scan from the Proxmox host that was never resolved. Three were uploads that each slipped past the expected lists in a different way, because each rule reads a different subset of about 12 overlapping "this is expected" mechanisms.
- **Noise records: about 1,860** (NOVEL_PROCESS_EGRESS, OFF_HOURS_ACTIVITY and NOVEL_DESTINATION make up 70%). No person or agent reads them.
- **Releases: 80** in 60 days. Most were hub-only, and most were detection logic or expected-list fixes.

**Recommended shape:**
- **Hub:** one Go hub doing one job. It ingests network telemetry, detects, pages through Aico, and keeps one expected-rule model as live data. It deploys like any other service (build, copy, restart) with no package signing.
- **Agents:** they collect and isolate, nothing more. Linux guests are updated through Aico fleet. Signed self-update stays only for the Windows laptops.
- **Aico:** it owns machine inventory, intent (always, on-demand, off) and liveness, so OmniNull stops keeping its own copy.
- **Removed:** the response authority, routine-key and hub-install-key ceremony, page budget, dead Nightshift routes and the noise detectors.
- **Added:** cheap high-signal tripwires (canary credentials, decoy addresses, domain intelligence on the DNS data the hub already collects), and a monthly live drill, so a page is known to work end to end.

Expected result: roughly half the code, releases only when agent code changes, and exceptions that never need a release.

### Milestones for builders

- **M1, unify "expected" (#1 and #3).** One `ExpectedRule {program: path glob [+ sha256 optional], destination: domain suffixes | AS | CIDRs, except: domain suffixes, hosts: endpoint ids or roles (default all), findings: types (default all), reason, expires (optional)}` stored in tuning. A single function, `Expected(finding)`, is called by every rule after the floor. Migrate quiet_pairs, quiet_clients, quiet_orgs, known_workloads, exclusions, agent_runtime_vendors and admin_fanout into it, then delete the old fields and the legacy migration maps. Mark as expected writes one rule, with the path pinned only if the agent recorded a hash, and no refusal for `/home`. Keep the floor (threat-intel match, sensitive ports, decoys, lab escape) unexemptable. Acceptance: the 30-day replay shows 0 pages for the 3 upload incidents, the floor drill passes, and the tuning has a single list. *Builder note: wait until the in-flight agy/Google maker change has landed, then fold its `exclude_domains` and `networks` into the rule shape.*
- **M2, noise off (#2).** Remove the off-hours detector and stop writing NOVEL_PROCESS_EGRESS, NOVEL_DESTINATION (except the `alert-disc-` new-LAN-device digest), BANDWIDTH_SPIKE and the record variant of AGENT_NEW_DESTINATION. Keep destination history. Remove their tuning fields. Delete stored record-class rows older than the retention period in one migration. Acceptance: the replay shows records per month under 150 and pages unchanged.
- **M3, service-style hub deploy (#4 and part of #7).** `scripts/deploy-hub.sh`: `go build`, then `scp` to CT 150 through `proxmox-gem` and `pct push`, swap the binary, restart, health-check `/api/v1/agents/update-status`, and keep the previous binary for rollback. No deb or version file for the hub; it reports its git sha. Remove `ominull-hub-install`, the hub-install keys and `dist/routine-keys.json` handling. Remove the hub deb's bundling of agent packages: the hub serves agent packages from a directory that the agent release fills. Acceptance: a hub-only change goes live in one command with no signing.
- **M4, agent release (rest of #7).** One release key, signed with `ominull-release-signer`. Linux agents on Proxmox guests and the workstation update through Aico fleet (root SSH plus `dpkg -i` of the signed deb); the hub's self-update path stays for the Windows endpoints only. Drop routine keys, the routine-key bootstrap branch and the canary-required rule, and keep an optional `--canary`. Delete `test-release-batching.sh` and its helper staging. Acceptance: a release of the agents alone, with the Windows laptops picking it up on their next check-in.
- **M5, Aico owns inventory (#6).** The hub reads `/api/status` machine rows and their intent (or Aico pushes intents into the hub's push reply). ENDPOINT_SILENT becomes "sensor dark": the agent is silent while Aico says the machine is up. Delete `presence` writes, `fleet_coverage.py` and its timer. Aico shows "machine has no OmniNull agent" from the hub's host list in its push. Acceptance: setting a guest to on-demand in Aico needs nothing in OmniNull.
- **M6, authority into hub (#5).** Requires owner decision 3. The hub holds an ed25519 grant key. Isolation, forensic and agent-update grants are signed in-process, using the same grant format so agents need no change. Delete `cmd/ominull-response-authority`, `responseauth` (approvals, TOTP, WebAuthn, sessions, learned and approval rules, auto-isolate book), `policyAuthorized` and the loosening machinery in `detection_policy.go` (keep the floor drill on save and the audit row). Migrate the tenant key so that existing agents keep verifying.
- **M7, dead routes and docs (#7).** Delete the Nightshift routes except `alerts/verdict` and `agent-builds`, and rename those two under `/api/v1/aico/`. Also delete the page budget health note, the `copilot.config` and legacy settings keys, and `docs/history`. Cut the docs to the README, `project-guide.md`, the threat model and one release runbook.
- **M8, tripwires (#8).** (a) Decoys: 2 unused LAN addresses and 1 lab address in `decoy_addrs`, plus a fake `Host` in `~/.ssh/config` pointing at one of them. (b) Canary credentials: a fake AWS key in `~/.aws/credentials` and a fake API token in a `.env` under `/srv/workspaces`. Use a self-hosted canary (the hub serves an endpoint the fake key's hostname resolves to via the router, and a hit pages) rather than a third-party service. (c) Domain intelligence: match abuse.ch ThreatFox and URLhaus domains against `dns_events`; a high-confidence match pages under the existing THREAT_INTEL_MATCH class. Put the feed URLs in tuning, not `netfeeds.go`.
- **M9, live drill (#9).** A script run monthly by Aico's scheduler from a lab guest. It triggers the four paths, checks that `aico_push_sent` grows and Aico shows the notices, then resolves the findings as `drill`. It writes a Status row ("drill passed", with the date).
- **M10, remote-admin features (#10). Owner decision 2026-11-06: keep them on every platform** (used remotely for emergencies, possibly incident response later). Nothing is deleted. Only tidy: keep them as one clearly separated module in hub and agent so detection code doesn't depend on them, and keep them working on Linux and Windows.
- **M11, console trim (#11).** Two agents, because of the 12K-line `app.js`. One cuts routes and APIs, the other cuts the UI.
- **M12, Go Linux agent (#12).** After M10. Collector (eBPF UDP and TCP counters, process attribution with exe sha256, DNS), isolation (nftables), heartbeat with certificate renewal, and grant verification. Run it beside the C agent on one lab guest and compare flow counts, then switch over. It must keep the remote-admin features (terminal, screen, scripts, maintenance) at parity before switching over, so weigh whether the rewrite still pays off before starting.

### Decisions only the owner can make

1. **Remote-admin features (terminal, screen, scripts, maintenance packages, data inventory): keep them for the Windows laptops, or delete them?** Recommendation was to delete them for Linux. **Answer (2026-11-06): keep them everywhere; don't delete.**
2. **Windows laptops: keep monitoring them with OmniNull?** They are often off, run old agents (1.8.97, 1.8.104 and a parked 1.8.92) and keep the Windows build and its signing alive. Recommendation: keep them. They are the household's least-controlled devices. The cost lands in M4 and M12.
3. **Retire the separate response authority (OK to fold grant signing into the hub)?** It changes a security boundary on paper. In practice it has signed everything automatically since 10-24, and it runs in the same container as the hub. Recommendation: yes.

### 3. Hardcoded values versus data

**Should be data** (live tuning, seeded by code):
- **Expected-list shapes:** the vendor fields and the split into quiet, pairs, workloads and exclusions. The values are already data, but every new kind of exception needs a new field, and therefore code. This is the root cause of the release churn. *(M1)*
- **`userWritablePrefixes`** (`storage/detection_tuning.go`): a decision, and on this host a wrong one. *(M1)*
- **Feed URLs and the pinned MISP commit** (`threatintel/netfeeds.go`). *(M8)*
- **`ROUTINE_CANARIES` default and `defaultRetiredKeys`:** environment data (goes away in M4).
- **Presence and role per endpoint:** they belong to Aico. *(M5)*

**Should stay code:**
- The floor (`detector/floor.go`: sensitive ports, sweep floor, unexemptable classes). It is a safety invariant that config must not loosen.
- The page, record and digest mapping in `class.go`, which is logic. Its thresholds are already data.
- Public-suffix validation of vendor domains.
- Protocol constants and the agent wire format.

**Delete:** `legacyQuietProcesses`, `legacyQuietPaths`, `legacyQuietOwners` and the migration code (production is migrated), plus the leftover settings keys (`copilot.config`, `legacy_agent_auth`, `nightshift_*`, `byte_*_repair_v1`, `anomaly_hunt_tier_backfill_v1`).

### 6. Ops

**How a release goes today** (`scripts/release.sh`, 414 lines):
1. Check that something shipped changed, and check the hub-install key.
2. Bump the version, run the quality gates and the Linux collector and isolation loops.
3. Build all native packages, then sign them (routine key, signed key list).
4. Verify a fresh install and the package lifecycle in an isolated root.
5. Install the hub through the Proxmox forced-command key (`ominull-hub-install`, 399 lines, Python).
6. Sync the package library and wait for the hub version.
7. Stage the agent rollout with canaries and wait for convergence.

Every hub change runs all of it.

**Breakage observed:** the 1.8.71 glibc build host, the 1.8.96 libbpf crash, the 1.8.70s key rotation (required a rotate-from path), today's self-test, and one false alarm that forced an urgent release (1.8.104: 42 pages in 7 days).

**Can Aico replace it?**
- **Hub:** yes. A service-style deploy over the root SSH agents already use, with the hub reporting its git sha in its machine row. Aico's `st service rebuild` targets local projects; a 40-line deploy script is enough here, with no new Aico feature needed.
- **Linux agents:** yes, through Aico fleet (root SSH to every Proxmox guest and the workstation).
- **Windows laptops:** no SSH, so they keep hub-driven signed self-update.
- **Status rows and pages:** already Aico's (`aico_push.go`, 1.8.106).

**Live state notes for builders:**
- Endpoint `status` reads `online` for hosts last seen days ago (laptops on 10-30 and 11-01). Use `last_seen_at`.
- `aico_push_sent` is empty: there have been no pages since push went live on 11-06.
- The tuning was last saved at 11-06 18:23 by the in-flight change.
